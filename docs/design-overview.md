# CaP-X 実装環境 設計概要

- 作成: 2026-11-10
- 対象: Agent 班メンバー、これから環境づくりに関わる人
- 位置付け: チーム内の要件定義書から、チームの設計判断と検証結果だけを抜き出した公開版。コンテストの規定や計算環境の詳細は、参加者向けの公式資料を正とし、本書には書かない。

## 1. 目的

コード生成型ロボットエージェント（以下 CaP-X。総称）の提出物は、1つのコンテナイメージ（Apptainer / Singularity の `.sif`）にまとめる。このため、チームの開発環境・作業手順・検査は「そのコンテナをどう作るか」から逆算して決める。

1. **提出イメージを、定義ファイルから再現可能に作れる状態にする。** これを環境の正(source of truth)とする。
2. **メンバーが開発したコードとモデルを、そのイメージに取り込む流れを決めておく。**
3. 公式の配布物（標準コード・評価コード）が出たら、すぐに差分確認 → 定義の修正 → 再ビルド → 配布に入れるようにする。

手元の Linux PC は、計算環境が使えるようになるまでの予行演習と、その後の早い確認の場とする。最終判断は計算環境で行う。

## 2. 設計の前提（チームの解釈）

- 評価はネットワークのない状態でコンテナの中で行われる前提で作る。依存パッケージと設定はすべてイメージ内に入れる。
- 公式の評価コードは改変しない。イメージには公式のものをそのまま入れ、ハッシュで改変がないことを確かめる。
- どのコミットからどの `.sif` を作ったかを必ず記録する（後からコードとイメージの一致を示せるようにする）。
- 公式の版・依存構成は配布後に確定する。それまでの定義は仮版で、差し替える前提。
- ローカル PC と計算環境の GPU で CUDA・PyTorch の対応版が一致する保証はない。CUDA は、関係するすべてのマシンのドライバが対応する版以下にする。

## 3. 用語

- **基盤イメージ（`base.sif`）**: ベースイメージ、CUDA・PyTorch、推論サーバー、シミュレータ、公式の評価コード、共通の依存を入れたイメージ。めったに変えない。
- **提出イメージ（`agent.sif`）**: 基盤イメージの上に、エージェントのコード・固有の依存・起動設定を重ねたもの。提出するのはこれ。モデル重みは入れない。
- **開発モード**: 基盤イメージに手元のコードをバインド(bind)で差し込んで動かす使い方。コードを変えるたびに再ビルドしなくてよい。
- **統合ビルド**: 指定したコミットから提出イメージを作り、バインドなし・ネットワーク遮断で動くかを確かめる手順。
- **チーム開発リポジトリ**: `env/`（環境）と `agent/`（エージェント）をまとめた非公開リポジトリ。

## 4. イメージの2段構成

| 段 | 中身 | 作る人・タイミング | 識別 |
|---|---|---|---|
| 基盤 `base.sif` | ベースイメージ（digest で固定）、CUDA・PyTorch、推論サーバー（vLLM）、Robosuite / LIBERO（BEHAVIOR は配布形式を見て判断）、公式の評価コード（固定コミットをビルド時に取得）、共通依存（ハッシュ付きロック） | 環境担当。公式の更新や共通依存の追加のとき | `base-YYYYMMDD.N` と SHA-256 |
| 提出 `agent.sif` | `Bootstrap: localimage` で基盤を土台に、`agent/` のコード（特定コミット）、固有の依存（`uv.lock`）、入口 | 統合ビルド。マージ時や提出候補を作るとき | 元コミット・基盤の版・重みの revision・SHA-256 |

- 2段に分けるのは、重い部分（CUDA・シミュレータ）を毎回作り直さず、エージェントの変更を短時間でイメージに反映するため。
- **モデル重みはイメージに焼き込まない。** 重みは「Hugging Face のリポジトリ・40桁の revision・コンテナ内のパス」で特定し、実行時に決めたパスへ読み取り専用でマウントする。開発やスモークテストでも同じパスにマウントして動かす。
- 版の入力（`env/versions.submission.env`）と、ビルドの結果（`env/images.lock`）は別のファイルにする。入力と出力を同じファイルにすると、版名が指すコミットと実際にビルドしたコミットがずれるため。
- ローカル PC 固有の版（ドライバ・Apptainer 等）は `env/versions.local.env` に分け、公式との差分確認の対象外にする。
- **版を固定する範囲**: ベースイメージはタグではなく digest、Python の依存はハッシュ付きのロックファイル、公式リポジトリはコミットで固定する。

## 5. ビルドと実行の場所

| 場所 | 基盤 | 提出 | 用途 |
|---|---|---|---|
| ローカル Linux PC（環境担当） | 定義からビルド | ビルド | 配布前の予行演習、以後の早い確認 |
| 計算環境の計算ノード | 同じ定義からジョブ内でビルド | ジョブ内でビルド | **正式なビルドと確認の場所**。ここで作ったものだけを提出候補にする |

- ローカルでビルドした `.sif` は転送しない。計算環境には定義ファイルとスクリプトを Git で渡し、同じものを作る。

## 6. リポジトリの構成と記録

```
env/                    環境担当が管理（変更は PR で環境担当のレビュー必須）
  base.def / agent.def  イメージの定義
  versions.submission.env / versions.local.env / images.lock
  requirements/         シミュレータの依存（ハッシュ付きロック）
  install-host.sh       ローカル Linux PC のホスト側セットアップ（冪等）
  jobs/                 ビルド・スモークテストのジョブスクリプト（手動でも Slurm でも同じ）
  tools/                差分確認、評価コードのハッシュ照合、イメージとコードの照合など
agent/                  Agent 班が開発
  pyproject.toml, uv.lock
  models.lock           重みのリポジトリ・revision・マウント先（重み本体は入れない）
  tests/
docs/                   メンバー向け・環境担当向けの手順書
```

- **リポジトリに入れないもの**: イメージ、モデル重み、実行記録、トークン、参加者限定資料。実行記録はリポジトリの外に置く（記録をコミットすると版が変わって再検査がくり返されるため）。
- **出自(provenance)の残し方**: 新しいコミットを作らずに残す。(1) 提出候補タグの注釈に元コミット・基盤の版・重みの revision・SHA-256 を書く。(2) `agent.sif` の `%labels` に元コミット・基盤の版・`models.lock` のハッシュを埋め込む。
- **公式配布物は取り込まない。** URL とコミットだけを記録し、ビルド時に公式リポジトリから取得する。公式の定義ファイルもコピーせず参照する。
- **トークン**: 各メンバーが自分で、対象リポジトリの読み取りだけに絞り、期限を付けて発行する。置き場所は各自のホーム領域（`~/.config/capx/`、ディレクトリ 700・ファイル 600）。共有領域・リポジトリ・ログ・イメージには置かない。ビルドで使った場合は、イメージに残っていないことを検査する。
- コミットのメールアドレスは GitHub の非公開アドレス（`…@users.noreply.github.com`）にする。

## 7. メンバーの開発を取り込む流れ

取り込みは「Git でコードを集め、決まった手順でイメージを作る」に一本化する。イメージを手で作り替えたり、コンテナ内で `pip install` した状態を持ち込んだりしない。

1. **開発**: `develop` から `feature/<内容>` を切り、開発モードで動かす。固有の依存は、基盤イメージの Python で作った仮想環境(venv)を作業領域に置いてバインドする。
2. **依存の追加**: 軽い Python パッケージは `agent/pyproject.toml`・`uv.lock` の PR。CUDA・シミュレータ・システムパッケージに関わるものは `env/` の PR として環境担当に依頼する。
3. **モデル重み**: `agent/models.lock` にリポジトリ・revision・マウント先を書く。重みは共有領域に取得しておき、読み取り専用でバインドする。
4. **PR とレビュー**: 軽量検査（`env/tools/lightweight_checks.sh`）を通し、レビューを受けてマージする。
5. **統合ビルド**: コミットかタグを指定し、**そのコミットの**ジョブスクリプトで提出イメージを作る。実行するのは誰でもよい。スクリプトは指定コミットを新しいディレクトリに取得し直し、未コミットの変更や手元で書き換えたスクリプトがあれば止まる。続けてバインドなし・ネットワーク遮断でスモークテストを行う。
6. **記録**: 元コミット・基盤の版・`models.lock` のハッシュ・SHA-256・結果をリポジトリ外の実行記録に残す。記録は実行ごとに別のディレクトリにし、上書きしない。
7. **提出候補**: 統合ビルドとスモークテストに通ったコミットにタグ `sub-YYYYMMDD.N` を付ける（付けるのは提出判断者だけ）。

ネットワーク遮断の方法は、(a) `apptainer exec --containall --net --network none`、(b) `--fakeroot` の併用、(c) `unshare -rn` の中で実行、の順に試し、通った方法を記録する。

### テストの回し方

- 1 枚の GPU を別々のジョブで同時に分け合うことは通常できないため、「テスト用 GPU」は運用で作る。テスト系のジョブは job array（`env/jobs/test_array.sh`）で同時実行数を絞り、GPU 1 枚までとする。
- 軽いテストは1つのジョブの中で並列に動かす（runner の `--trials`・`--parallel`）。
- GPU が要らない作業（ビルド・軽量検査・単体テスト）は、CPU のパーティションがあればそちらへ回す。

## 8. 実行時の構成（推論サーバーを1つ共有する）

- 提出イメージの入口は「推論サーバーを1つ起動 → 重みの読み込み完了を待つ → 試行を並列に処理する」の構成にする。
- **試行どうしの独立**: 試行ごとに新しいプロセスと一時ディレクトリを使い、終了時に消す。試行をまたぐメモリ・ログ・キャッシュ・データベースを持たない。同時に走る試行どうしでやり取りしない。アプリケーション側で推論結果をキャッシュする仕組みは作らない。
- 並列数は、GPU メモリ（重み・KV キャッシュ・シミュレータ×並列数）と処理速度を測って決める。
- 評価コードが試行をどう起動するかは配布物で確認し、入口の最終形を決める。

## 9. 公式配布の直後の流れ

1. 公式リポジトリを clone し、URL とコミットを `versions.submission.env` に記録する。
2. 差分確認スクリプト（`env/tools/diff_versions.py`）で、公式の依存・版・ベースと本環境の差分を一覧にする。
3. 差分を `env/` に反映し、ローカルで再ビルドしてスモークテスト。
4. 同じ定義で計算ノードで基盤イメージをビルドし、評価コードの SHA-256 が公式と全件一致することを確かめる。
5. 版を付けて配布・通知する。

| 段 | 条件 |
|---|---|
| 1段目 | 公式コードが動く基盤イメージが、計算ノードでスモークテストを通る |
| 2段目 | 1段目に加え、参照実装の1試行と、仮のエージェントでの統合ビルドが計算ノードで1周通る |

## 10. 非機能要件

- **再現性**: イメージは定義ファイルと版ファイルからのみ作る。手作業で変えたイメージを提出候補にしない。
- **冪等性(idempotency)**: `install-host.sh` とジョブスクリプトは再実行しても同じ状態に収束する。
- **オフライン動作**: 提出イメージはバインドなし・ネットワーク遮断で動くこと。開発モードで動いただけでは合格にしない。
- **`.sif` とコードの一致の示し方**: SHA-256 は再ビルドで変わるため照合に使えない。代わりに `%labels` の出自と、イメージ内のコードのファイルごとの SHA-256 一覧を元コミットと照合する（`env/tools/sif_code_check.py`）。
- **機密性**: リポジトリはいずれ公開される前提で中身を決める。限定資料・未確認の配布物・秘密情報・メンバーのアカウント名をファイルに書かない。
- **文書化**: 班長が不在でもメンバーが再現できる形で手順を残す。

## 11. ローカル Linux PC での検証結果（2026-11-10）

検証環境: Ubuntu 26.04、NVIDIA RTX PRO 4500 Blackwell（32GB）、ドライバ 595.99（CUDA 13.2 まで）。

| 項目 | 結果 |
|---|---|
| ホスト基盤 | Apptainer 1.5.5（公式 .deb、SHA-256 照合）、uv 0.13.7。同梱の AppArmor プロファイルで権限なしの `--fakeroot` ビルドが通る。ネットワーク遮断は方法 a が権限なしで使え、方法 c は AppArmor に止められる |
| 基盤イメージ（仮版） | 仮ベース `nvcr.io/nvidia/vllm:26.05.post1-py3`（digest 固定、CUDA 13.2.1）。Python 3.12.3、PyTorch 2.12.0a0、vLLM 0.21.0。9.34GB、ビルド約 200 秒 |
| シミュレータ | ネットワーク遮断・画面なし（EGL）で、Robosuite 1.5.2（Lift）と LIBERO（libero_spatial）の最小エピソードが動く。LIBERO は別の仮想環境（Python 3.10・robosuite 1.4.0・CPU 版 torch） |
| 再現性 | 再ビルドで、版の違いは意図的にずらした1行だけ |
| 統合ビルド | 指定コミットから `agent.sif` を作り、出自・コード一致・トークンなし・実行のすべてが合格。小型モデル（Qwen2.5-0.5B-Instruct、読み取り専用マウント）の推論サーバーが 37 秒で起動し、4 試行を並列 2 で処理。試行ごとの一時ディレクトリは別々で、終了時に削除 |
| 負のテスト | 手元で書き換えたスクリプト・未コミットの作業ツリー・コミットの不一致で、正しく止まる |
| 配布の模擬（ドライラン） | 使い捨てのリポジトリで、差分検出からビルド・照合まで 12 項目すべて合格 |
| テストの一括実行 | `test_array.sh` を Slurm なしで2タスク実行し合格 |

### 実装中に分かったこと

- Apptainer はタグと digest を併記したイメージ名を受け付けない（`From` はリポジトリ名＋digest にする）。
- ホストの `/tmp` に容量制限があることがあり、ビルドの作業領域はデータ領域に置く。
- numba のキャッシュは書き込める一時領域に向ける（`NUMBA_CACHE_DIR`）。
- LIBERO の仮想環境ではベースの `LD_LIBRARY_PATH` を外す起動ラッパーが必要（PyTorch の共有ライブラリの取り違えを防ぐ）。
- vLLM 0.21 では `--disable-log-requests` が廃止されている。
