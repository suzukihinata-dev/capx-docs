CaP-X 本番コンテナ アーキテクチャ

チームの設計概要（docs/design-overview.md）を図にしたもの。正(source of truth)は GitHub の定義ファイルで、正式なビルドと確認は計算環境の計算ノードで行う。点線はまだ確認できていない経路。

メンバー開発の取り込み

  1. develop から feature ブランチを切り、開発モード（base.sif ＋ コードのバインド）で動かす
  2. 軽い Python 依存は agent/ の uv.lock、CUDA・シミュレータ系は env/ を変える PR を環境担当へ
  3. 重みは Git にもイメージにも入れず、HF のリポジトリと revision を models.lock に書く。実行時は決めたパスに読み取り専用でマウントする
  4. PR で軽量検査とレビューを通して develop へ
  5. 誰でも、コミットかタグを指定して、そのコミットの env/jobs/ で agent.sif をビルドし、バインドなし・ネットワーク遮断でスモークテスト（未コミットの変更があれば止まる）
  6. 結果はリポジトリ外（records/）に記録。出自（commit・基盤の版・重みの revision・.sif ハッシュ）は提出候補タグの注釈と agent.sif の %labels に残す

ジョブ投入の分担

  • 各メンバーが自分のアカウントと鍵でジョブを投入（共有しない）
  • 基盤イメージの更新だけは環境担当
  • テスト系は GPU 1 枚まで。複数のテストは job array（test_array.sh）で同時実行数を絞る
  • GitHub・HF のトークンは各自が読み取り専用で発行し、自分のホーム領域に置く（共有領域・リポジトリ・イメージに置かない）

公式配布への対応

  1. 公式リポジトリを clone し、コミットを versions.submission.env に記録（取り込まずに参照）
  2. 差分確認で版のずれを一覧化し、env/ を更新する PR
  3. ローカル Linux PC で早く確認 → 計算ノードで正式にビルド
  4. 評価コードの SHA-256 を公式と照合（改変なしの確認）
  5. 1段目: 公式コードが動く基盤イメージ（base-YYYYMMDD.N）を配布。2段目: 参照実装が1試行動く版
