# capx-team リポジトリ解説

- 作成: 2026-11-10（この時点のリポジトリの状態の解説。最新の内容はリポジトリ本体の README・docs/ を優先）
- 対象: Agent 班メンバー（リポジトリ本体は非公開。招待されたメンバーのみ閲覧できる）

## 1. このリポジトリで何をしているか

チームの提出物は Singularity イメージ（`agent.sif`）です。このリポジトリは、そのイメージを「定義ファイルから、誰が・どのマシンで・いつビルドしても同じものができる形」で作るためのものです。

中心になる考え方は2つです。

- コード（`agent/`）と環境（`env/`）を分ける。環境は環境担当が管理し、勝手に変えられない。
- 「手元で動いた」は合格ではない。指定したコミットでイメージをビルドして動いたものだけが成果物。そのため日常の開発では再ビルド不要の「開発モード」が使え、提出の判定は「統合ビルド」で行う。

Git に入れないものが3つあります。イメージ（`*.sif`）、モデル重み（`*.safetensors` 等）、実行記録（`records/`）です。

重みは `agent/models.lock` に「どのリポジトリの・どの revision を・どこにマウントするか」だけを書き、ビルドや評価の時に取得・マウントします。実行記録はリポジトリの外に置きます。これでリポジトリは軽いまま、再現に必要な情報だけが残ります。

## 2. ルートのファイル

- `RULE.md` — 全員と AI エージェントが守るルール。「絶対に守ること」「コミットと PR の規約」「計算環境の決まり」「コンテストルールの要約」からなる。疑問があれば班長に確認。
- `AGENTS.md` / `CLAUDE.md` — `RULE.md` へのリンク。Claude Code・Codex などの AI エージェントがこのリポジトリで作業するときに自動的に読み込まれる。AI エージェントを使うのに特別な設定は不要。
- `README.md` — リポジトリの全体像と、GitHub の運用ルール（Gitflow）。
- `.gitignore` — イメージ・重み・実行記録など入れてはいけないものの指定。ただし .gitignore だけに頼らず、軽量検査でも機械的に確認する。

## 3. `agent/` — メンバーが開発する場所

- `capx_agent/` — エージェント本体。`runner.py` が実行の入口、`trial.py` が1試行、`models.py` が重みの読み込み。
- `models.lock` — 評価時にマウントする重みの一覧。1行1モデルで「Hugging Face のリポジトリ・40桁の revision・コンテナ内のパス」。重み本体はここに入れない。
- `pyproject.toml` / `uv.lock` — Python の依存。パッケージを足すときは `pyproject.toml` に書いて `uv lock` で更新し、PR に含める。
- `tests/` — 単体テスト（軽量検査で走る）。

## 4. `env/` — 環境担当が管理する場所（変更は PR + 環境担当のレビュー必須）

- `base.def` — 基盤イメージの定義。CUDA・PyTorch・推論サーバー・シミュレータ（Robosuite・LIBERO）・評価コードまで入る。ベースはタグではなく digest で固定。
- `agent.def` — 提出イメージの定義。基盤イメージ + `agent/` のコード。重みは入れない。
- `versions.submission.env` — 提出側・計算環境側と合わせる版（ベースイメージ、シミュレータの版など）。公式配布の後に、公式環境との差分確認の結果で更新される。
- `versions.local.env` — 各自の Linux PC 固有の版（ドライバ・Apptainer・uv の導入情報）。公式との差分確認の対象外。
- `requirements/` — シミュレータの Python 依存。`.in` が入力、`.txt` がハッシュ付きのロック。
- `images.lock` — ビルド結果の記録（タグ・SHA-256・サイズ・ビルド元コミット）。基盤イメージを作るたびに1行追加される。`base-YYYYMMDD.N` はこの記録の版名で、git タグではない。
- `jobs/` — ビルド・検査のジョブスクリプト。手元でも Slurm（計算環境）でも同じものを使う。`build_base.sh`（基盤ビルド）、`build_agent.sh`（提出イメージ）、`integration_build.sh`（統合ビルド）、`smoke_test.sh`（スモークテスト）、`test_array.sh`（テストの一括実行）、`place_base.sh`（イメージの配置）。手順を変えたら `JOB_PROTOCOL_VERSION` が上がる。
- `tools/` — 支援ツール一式。`lightweight_checks.sh`（PR 前の軽量検査）、`diff_versions.py`（公式配布との差分確認）、`eval_code_hash.py`（評価コードのハッシュ管理）、`models.py`（重みの取得・バインド・submission.yaml 生成）、`sif_code_check.py`（イメージとコードの照合）、`check_secrets_in_sif.sh`（イメージ内の秘密情報チェック）など。
- `smoke/` — Robosuite・LIBERO の最小エピソード（スモークテスト用）。
- `install-host.sh` — Linux PC にホスト基盤（Apptainer・uv）を入れるスクリプト。再実行しても変わらない（冪等）。
- `eval_code.sha256` — 公式評価コードのハッシュ一覧。公式配布の後に作る（現状は空）。

## 5. `docs/` — 手順書

- `member-guide.md` — メンバーの手順。初回準備、開発モード、依存・重みの変え方、PR、統合ビルド、計算環境の決まり、テストの回し方。
- `env-maintainer.md` — 環境担当の手順。基盤イメージの更新、公式配布への追従、実行記録の移動。

## 6. 日常の流れ（要約。詳細は member-guide.md）

初回に1回だけ:

1. リポジトリへの招待を受ける。コミットメールを GitHub の非公開アドレス（`…@users.noreply.github.com`）に設定。
2. 計算環境の自分のアカウントを準備し、自分の PC で作った SSH 鍵を登録（鍵・アカウントは共有しない。手順は班長からの案内）。
3. トークン（GitHub 読み取り専用・Hugging Face 読み取り）を計算環境の自分のホーム領域 `~/.config/capx/` に配置。

開発の1サイクル:

1. `develop` から `feature/<内容>` を切る。
2. 開発モード（基盤イメージにコードを差し込む `apptainer exec`。再ビルド不要）で動作確認。
3. `bash env/tools/lightweight_checks.sh` を通す。
4. PR を出す。`agent/` の変更は Agent 班メンバー1人以上の承認、`env/` の変更は環境担当の承認が必須。squash merge で `develop` へ。
5. 提出候補は `develop` から `release/sub-YYYYMMDD.N` を切り、統合ビルド・スモークテスト・提出前検査をすべて合格させて `main` へ。`main` のコミットに `sub-*` のタグが付く。

## 7. 計算環境の決まり（member-guide §6・§7 より）

- ジョブの投入は班長の利用開始の案内から。利用ルール（ログイン、ログインノードでしてはいけないこと）は、参加者向けの資料・班長の案内と `RULE.md` に従う。
- テスト系は GPU 1枚まで。複数のテストは `test_array.sh`（job array で同時実行数を絞る）で流す。残りの GPU は学習・本番相当の評価に使う。
- GPU が要らない作業（ビルド・軽量検査・単体テスト）は CPU パーティションに回す。

## 8. AI エージェントを使うメンバーへ

- `RULE.md` が自動的に読み込まれるため、特別な指示は不要。ただし、AI エージェントが独自の判断で `sbatch`・`srun`・`scancel` を実行すること、GitHub の設定（可視性・保護・remote 等）を変えることはルールで禁止されている。
- AI エージェントやモデルの使い方には、コンテストのルールによる制限がある。`RULE.md` の要約と参加者向けの公式資料を確認する。

## 9. 公式配布で何が変わるか

- 公式の標準コード・評価コードが GitHub で配布される。このリポジトリは公式のファイルをコピーせず、`versions.submission.env` の `OFFICIAL_REPO_URL`・`OFFICIAL_COMMIT` で参照する。
- 環境担当が差分確認（`diff_versions.py`）を行い、必要に応じてベースイメージや依存を更新して基盤イメージを作り直す。
- メンバーがすることは、新しい基盤イメージの配置通知（Slack）を受け取ったら、開発モードで使うイメージを切り替えることだけ。

## 10. 困ったとき

- 手順・ルールに書かれていないことや、例外・解釈が絡む判断は、勝手に決めず班長に確認する。
- まず読むもの: リポジトリの `RULE.md` → `README.md` → `docs/member-guide.md`。
